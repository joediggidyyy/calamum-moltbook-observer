## 1) Purpose

This document defines **how Calamum work is executed when CodeSentinel is the job orchestrator**.

It is specifically meant to eliminate drift where:

- a QuestStack exists but cannot pass CodeSentinel gates,
- evidence artifacts exist but are not linked consistently,
- secrets/env vars are handled in ways that violate Calamum + CodeSentinel policy,
- “project locality” rules conflict with system-level evidence paths.

This is a policy/operations contract: **it is about execution expectations and compliance**, not architecture prose.

## 2) Canonical execution surfaces (SSOT)

### 2.1 Task SSOT (job lifecycle entry point)

- **SSOT file**: `operations/tasks.json`
- Each record contains (at minimum):
  - `id` (task_id)
  - `path` (QuestStack markdown path)
  - `status` (open / planned / in-progress / completed)

A CodeSentinel-managed job is started/closed against **task_id**, and the lifecycle gates use `task.path` to locate the QuestStack.

### 2.2 QuestStack is the parse surface for PRE_JOB

The CodeSentinel PRE_JOB gate parses the QuestStack markdown for artifact references.

**Minimum required** (fail-closed if missing):

- a QuestFrame spec path (must match the allowed patterns)
- a repo-root job stub under `jobs/` (see §3.3)
- a job report under `docs/reports/operations/`
- a QuestStack provenance log under `logs/queststack/`
- a QuestStack evidence JSONL under `logs/queststack/`

## 3) Artifact spine requirements (what every Calamum QuestStack must include)

### 3.1 Required linked paths (names-only)

Every Calamum QuestStack document under:

- `projects/calamum-moltbook-observer/queststacks/*.md`

MUST include an “Artifacts (gate-critical)” section that explicitly links:

1) **QuestFrame spec** (required by gate regex)
- `projects/calamum-moltbook-observer/questframes/<QF-ID>.json`

2) **Job doc stub (repo-root, PRE_JOB)**
- `jobs/<CALAMUM_JOB_xxxx...>.md`

3) **Project job SSOT docs (paired)**
- `projects/calamum-moltbook-observer/jobs/<CALAMUM_JOB_xxxx...>.md`
- `projects/calamum-moltbook-observer/jobs/<CALAMUM_JOB_xxxx...>.json`

4) **Job report (execution narrative stub)**
- `docs/reports/operations/JOB_REPORT_<QS-ID>.md`

5) **QuestStack provenance artifacts**
- `logs/queststack/<QS-ID>_log.md`
- `logs/queststack/<QS-ID>_evidence.jsonl`

6) (Recommended) **Canonical gate evidence stream**
- `logs/behavioral/gates/gate_events.jsonl`

### 3.2 “Project locality” vs system-level evidence (conflict resolution)

Calamum project directives require runtime data/logs to live under the project root:

- `projects/calamum-moltbook-observer/local_untracked/` (analysis artifacts)
- `projects/calamum-moltbook-observer/logs/` (runtime logs)

However, CodeSentinel’s umbrella job lifecycle intentionally writes **system-level evidence** at repo-root:

- `docs/reports/operations/` (job reports)
- `logs/queststack/` (quest provenance log/evidence)
- `logs/behavioral/gates/` (gate evidence)

**Policy resolution**:

- Project runtime outputs (data, model artifacts, app logs) MUST remain inside the project tree.
- System-level evidence artifacts generated by CodeSentinel gates/orchestration MUST remain in the umbrella repo-root locations.

This is not optional; it is required for consistent governance across all CodeSentinel-managed domains.

### 3.3 Important: how the gate detects `jobs/`

The PRE_JOB gate searches the QuestStack markdown for the first substring `jobs/` and treats it as the job doc link.

Therefore:

- A link like `projects/calamum-moltbook-observer/jobs/...` is **not sufficient** by itself.
- The QuestStack MUST explicitly include `jobs/<...>.md`, and that file MUST exist.

## 4) Job lifecycle expectations (operator workflow)

### 4.1 Start / execute / close

For any CodeSentinel-managed Calamum task:

- Start: `codesentinel job start <task_id>`
- Close: `codesentinel job close <task_id>`

Gates are executed as part of job lifecycle.

### 4.2 Mandatory evidence steps

- Gate evidence is append-only and names-only:
  - `logs/behavioral/gates/gate_events.jsonl`
- QuestStack provenance artifacts must exist and stay current:
  - `logs/queststack/<QS-ID>_log.md`
  - `logs/queststack/<QS-ID>_evidence.jsonl`

### 4.3 Post-job health check

After closing a job:

- Run SessionMemory health:
  - `codesentinel memory health --json`

(Operators should keep `.agent_session/policy_snapshot.*` and `.agent_session/ops_awareness.*` fresh throughout execution.)

## 5) Security rules (Calamum-specific emphasis)

### 5.1 Names-only doctrine

- Never write secrets/tokens/keys/hostnames/usernames/IPs into tracked files.
- Evidence is path-based and presence-based.

### 5.2 Secret handling (KEYSMITH doctrine)

For LIVE collection, `MOLTBOOK_API_KEY` must be obtained without humans handling the secret.

Approved model:

- KEYSMITH mints/obtains the key inside a sandbox.
- Humans may complete a vendor claim ceremony using **claim_url only** (non-secret).
- The secret is transferred via sealed drop and imported into VAULT / OS secret storage.

Hard stops:

- If the secret key is printed, logged, or written to a tracked path.
- If any workflow requires a human to copy/paste or view the key.

### 5.3 Network notes

- ICMP is assumed unavailable. Do not use `ping` as a liveness check.
- Connectivity checks must use approved TCP/SSH or higher-level probes, and only where allowed.
